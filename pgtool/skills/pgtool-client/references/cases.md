# 案例

本页是客户端日常任务的做法。测试失败与同步失败的诊断见 diagnosis.md。程度分「可做」「部分可做」「暂不可做」。接口见 api.md。

## 案例 1：了解这台电脑的环境

- 问题：「这台电脑现在在做哪个工单？」
- 做法：读服务就绪、产线身份、生产上下文。生产上下文中的字段：`orderNumber`（工单号）、`productModel`（型号）、`orderQuantity`（数量）、`operatorName`（操作员）、`orderValid`（工单是否有效）。
- 同时看 `productDefinition`、`productionConfig`：字段全为空串表示尚未绑定产品定义或生产配置，可能影响能否测试，应提示用户。
- `cloudSync.lastError` 是这台电脑最近一次连接云后台的结果，只有错误码、没有时间，可顺带说明。
- 程度：可做。
- 注意：问「能不能测」时，转到案例 5。

## 案例 2：看一个测试流程里有什么

- 问题：「某项目的主流程有哪些步骤？」
- 做法：
  1. 定位项目 ID（字段 `projectId`）。项目列表很大，常常读不全；按用户给的名称先匹配 `name`，匹配不到再看 `description`。有多个候选或都不完全相符时，列出候选（名称与 ID）请用户确认，或说明你按哪一个回答。用户能直接给出项目 ID 时跳过这一步。
  2. 读该项目的工作流列表（工作流在 `value` 中），找到入口工作流（`isEntry: true`）。
  3. 先用 `depth=3` 读大纲看规模；如果最深一层仍有 `childCount` 大于 0 而未展开，直接改用 `depth=10` 一次读全。
  4. 入口工作流常是多层骨架（并行、循环、等待触发、派发），真正的测试步骤在被派发的工作流里（例如「测试调度」）。看到派发节点时，在工作流列表找到目标工作流，同样读大纲。
  5. 步骤顺序按大纲中 `children` 的先后。
  6. `catch`（异常收尾）、`finally`（收尾）、`return` 不是测试步骤，单独列为收尾。
  7. 看到 `loop` 里套着等待触发，表示每测一台都重新等待触发。
- 程度：可做。
- 注意：项目的 `description` 是作者填写的说明，可能过期；以大纲为准，发现不一致时告诉用户。

## 案例 3：判断某个流程是否已部署最新内容

- 问题：「这个项目在这台电脑上部署的是最新的吗？」
- 做法：
  1. 项目内容时间：工作流列表返回体**顶层**的 `revision`（不在每个工作流里），冒号后的时间是内容最后修改时间。不要用项目的 `metadata.updatedAt`，它可能滞后。
  2. 找本机实际在用的部署：没有直接接口，执行类接口又必须先知道部署，所以从记录入手。最近一条测试记录的 `sessionId` 形如 `production-test:{deploymentId}:run:{runId}`（`rawEntity.identity` 中也有 `ProjectId`、`DeploymentId`）。用这个部署查活跃执行；有活跃执行（如 `runtimeStatus: Waiting`）是「这台电脑正在用这条部署」的最强证据。
  3. 看这条部署属于哪个项目（单个部署的 `projectId`）。不是用户问的项目时，告诉用户：本机当前在用的是另一个项目。
  4. 用户问的项目的部署：部署列表按部署 ID 排序，与时间无关，需要在列表中按 `projectId` 筛出后比较 `deployedAt`；传 `projectId`、`limit` 不会报错，但不生效。可对最晚的几条查最近执行，看是否在本机运行过；查到 `recent-not-found` 只说明这几条没运行过，不能推及全部。
  5. `status: active` 只说明部署记录有效，不等于正在使用；历史部署通常也都是 `active`。
  6. 部署的 `definitionHash` 与项目 `revision` 是两套不同的值，不能直接比较，只能比时间。
- 证据强弱：活跃执行 > 最近测试记录 > 部署列表。
- 结论口径：可以说「最近运行的部署晚于（或早于）内容修改时间」；不能断言「正在用的就是最新」，并说明原因。
- 程度：部分可做。

## 案例 4：修改流程中的某个步骤

- 问题：「把等待时间从 5 秒改成 10 秒。」
- 做法：用大纲和节点定位该步骤，向用户确认；给出修改建议（节点、字段、原值、新值）；说明修改后需发布并部署才会在产线生效。
- 程度：部分可做。只给建议，由用户在编辑器中修改。

## 案例 5：能不能测，以及启动测试

- 你不能启动、停止、终止或重试测试；即使条件全部满足，也要请用户在界面操作。
- 前提检查清单：

| 检查项 | 怎么查 | 不满足时 |
|---|---|---|
| 服务就绪 | 就绪接口 `status: ready` | 阻塞 |
| 产线身份 | 身份状态 `active` | 阻塞 |
| 工单有效 | 生产上下文 `orderValid` | 阻塞 |
| 工单型号与要测的项目相符 | 没有字段关联型号与项目。能查到的是本机实际在用的项目：最近记录或活跃执行的 `projectId` | 把工单型号和实际在用的项目一起告诉用户，请用户确认是否相符；不要自行判定相符或不符 |
| 产品定义与生产配置已绑定 | 生产上下文中两者字段非空 | 很可能阻塞，标为推测 |
| 项目有可用部署 | 单个部署 `status: active`、`releaseAvailability: verified` | 阻塞。历史部署通常也满足，所以这一项只能排除「没有部署」 |
| 当前会话状态 | 从最近记录得到部署，查活跃执行；没有列出全部活跃执行的接口 | 活跃执行 `Waiting` 是常驻会话在等触发，属正常；其工作台 `executionFailures` 有失败时按 errors.md 第 3 节转述；未查过的部署写「未知」 |
| 上一次运行结果 | 最近一条测试记录 | 失败时提醒用户先处理 |
| 设备在线 | 当前无接口；单个部署的 `appliedLocalBindings.devicePortMappings` 列出绑定的设备端口，可提示用户逐一检查；两个设备映射到同一个端口时特别指出 | 写「未知」，请用户在界面确认 |
| 云后台可达 | `cloudSync.lastError` | 不阻塞启动，但记录传不上去 |

- 型号目录接口当前返回空，不能用来核对型号。
- 回答「能不能测」时，结论只用三种之一：「满足已查条件，可以在界面启动」「有阻塞项，先处理」「有未知项，请在界面确认」，并附上清单。
- 程度：前提检查部分可做；启动不开放。

## 案例 6：遇到云后台的问题

- 问题举例：「这周全线合格率是多少？」「其他电脑的记录传上去了吗？」「云端能查到这条记录吗？」「产品定义怎么改？」
- 做法：
  1. 告诉用户这属于 PgTool 云后台，当前只能看到这台电脑的数据，请在云后台查看。
  2. 如果这台电脑有相关的局部信息，可以补充，但必须标明「仅这台电脑」。例如：这台电脑同步队列的失败情况、本机记录统计。
  3. 不要用本机数据推断云端结论，例如不能把本机合格率说成全线合格率，也不能因为本机同步失败就断言云端没有某条记录。
  4. 本机统计只给记录条数，不分合格与不合格；不要承诺「本机合格率」，也不要拿最近几条记录的抽样冒充统计。
- 程度：不在客户端范围，按上述方式说明。
